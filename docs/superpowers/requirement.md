## 1. เป้าหมายและขอบเขต

สร้างเว็บไซต์ศูนย์รวมความรู้ที่เจ้าของจัดการข้อมูลผ่านระบบหลังบ้านได้ โดยเผยแพร่บทความ เอกสาร PDF รูปภาพ และไฟล์ประกอบ จัดหมวดหมู่ ค้นหา ดาวน์โหลด และทำแบบทดสอบเพื่อการเรียนรู้ได้ ใช้งานสะดวกทั้งมือถือ แท็บเล็ต และคอมพิวเตอร์

บุคคลทั่วไปเข้าชมเว็บไซต์ ค้นหา และอ่านเนื้อหาสาธารณะได้โดยไม่ต้องล็อกอิน แต่ก่อนดาวน์โหลดไฟล์เอกสารหรือไฟล์แนบทุกประเภทต้องล็อกอินด้วยบัญชีที่ยืนยันตัวตนแล้วเสมอ โดยสมัครได้ด้วยอีเมล เบอร์โทรศัพท์ หรือบัญชี Google เจ้าของกำหนดไฟล์แยกเป็นสำหรับสมาชิกทั่วไปหรือ VIP และตรวจสอบสิทธิ์ที่ฝั่งเซิร์ฟเวอร์ทุกครั้ง

เอกสารนี้เป็นข้อกำหนดและแนวทางออกแบบตามภาพอ้างอิงที่ผู้ใช้ส่งมา ผลส่งมอบในขั้นนี้คือไฟล์ Markdown และ PDF เนื้อหาเดียวกัน ส่วนการสร้างเว็บไซต์จริงอยู่ในขั้นพัฒนาถัดไป

### 1.2 สมมติฐานที่ใช้กำหนดขอบเขตเริ่มต้น

- บุคคลทั่วไปหมายถึงผู้เข้าชมที่ยังไม่เข้าสู่ระบบ ส่วนสมาชิกทั่วไปหมายถึงผู้สมัครและเข้าสู่ระบบแล้ว
- การสมัครทั้ง 3 ช่องทางอยู่ในขอบเขตรุ่นแรก เลือกใช้ช่องทางใดช่องทางหนึ่งได้ ไม่บังคับให้กรอกทั้งอีเมลและเบอร์โทรศัพท์
- เนื้อหาเป็นข้อมูลความรู้และเอกสารเผยแพร่ CMS ใช้งานโดยเจ้าของและทีมงาน
- เจ้าของหรือ Admin อนุมัติและกำหนดวันหมดอายุ VIP ด้วยตนเอง
- แบบทดสอบใช้เพื่อการเรียนรู้ และการค้นพบผ่าน AI ภายนอกอยู่ในขอบเขตเตรียมเนื้อหาเว็บให้ค้นหาได้
- ค่าขนาดไฟล์ จำนวนข้อมูล และเป้าหมายประสิทธิภาพในเอกสารเป็นค่าเสนอเริ่มต้น ปรับได้เมื่อทราบปริมาณใช้งานจริง

### 1.3 สิ่งที่ไม่อยู่ในรุ่นแรก — รายการกลางสำหรับประเมินราคา

รายการนี้เป็นขอบเขตยกเว้นหลัก การอธิบายเทคโนโลยีหรือแนวทางต่อยอดที่อื่นไม่ถือว่าเพิ่มรายการเหล่านี้ในงานรุ่นแรก

- ระบบทำบัญชี ยื่นภาษี หรือประมวลผลธุรกรรมทางการเงิน
- การรับชำระเงินค่าสมาชิก การต่ออายุแบบตัดเงินอัตโนมัติ และระบบขาย/คิดเงินพื้นที่โฆษณา
- แอปติดตั้งบนมือถือหรือคอมพิวเตอร์; รุ่นแรกเป็นเว็บไซต์ responsive ผ่านเบราว์เซอร์
- แชต AI สรุปเอกสารด้วย AI และ MCP server สำหรับ AI ภายนอก
- OCR และการค้นข้อความภายใน PDF/ภาพสแกน; รุ่นแรกค้น metadata และข้อความบทความตามสิทธิ์
- ใบประกาศ ข้อสอบรับรองวิชาชีพ คำถามหลายคำตอบ คำตอบอธิบาย และการตรวจโดยผู้สอน
- ผู้ใช้ทั่วไปอัปโหลดหรือเผยแพร่เนื้อหาเอง
- การแสดงตัวอย่าง DOCX/XLSX/PPTX ออนไลน์ ลายน้ำเฉพาะบุคคล และระบบเวอร์ชันเอกสารขั้นสูงเกิน FR-01/FR-02
- ปฏิทินภาษี อีเมลแจ้งเนื้อหาใหม่ การแจ้งเตือน VIP ใกล้หมดอายุ และโฆษณาตามพฤติกรรม
- บทบาทแบบกำหนดสิทธิ์เอง และภาษาไทยสำหรับ UI หน้าเว็บ/หลังบ้าน; รุ่นแรกใช้บทบาทคงที่และ UI ลาว/อังกฤษ
- บริการแปลเนื้อหาทั้งคลังและการรับประกันอันดับ Google/การอ้างอิงโดย AI ภายนอก เจ้าของจัดเตรียมคำแปลที่ตรวจทานแล้ว

## 3. ผู้ใช้และสิทธิ์การเข้าถึง

### 3.1 บทบาทในระบบ

| กลุ่ม | สิทธิ์หลัก |
|---|---|
| Guest — บุคคลทั่วไป | เข้าชมเว็บไซต์ อ่านเนื้อหาสาธารณะ ค้นหา อ่านข้อมูลตัวอย่าง และสมัครสมาชิก; ดาวน์โหลดไฟล์แนบไม่ได้ |
| Member — สมาชิกทั่วไป | สิทธิ์ Guest พร้อมอ่านรายการสำหรับสมาชิก ดาวน์โหลดไฟล์ Member หลังล็อกอินและยืนยันตัวตน บันทึกบทความ และดูประวัติแบบทดสอบตนเอง |
| VIP — สมาชิก VIP | สิทธิ์ Member พร้อมอ่าน/ดาวน์โหลดรายการ VIP ขณะที่สถานะยังไม่หมดอายุ |
| Editor — ผู้จัดทำเนื้อหา | สร้างและแก้ไขร่าง อัปโหลดไฟล์ จัดทำคำถาม ส่งให้ตรวจ และดูตัวอย่างผ่านหลังบ้าน |
| Admin — ผู้ดูแล | ตรวจและเผยแพร่เนื้อหา จัดหมวด จัดการสมาชิก อนุมัติ VIP และดูรายงาน; เข้าได้หลังผ่าน TOTP หรือรหัสกู้คืน |
| Owner — เจ้าของ | สิทธิ์ Admin พร้อมจัดการบัญชีทีมงาน มอบหมายบทบาทคงที่ และค่าตั้งระบบ; เข้าได้หลังผ่าน TOTP หรือรหัสกู้คืน |

สิทธิ์ทีมงานและระดับสมาชิกต้องเก็บแยกกัน การเป็น VIP ไม่ได้ทำให้เข้าหลังบ้านได้ รุ่นแรกบทบาทและสิทธิ์คงที่: Editor สร้าง/แก้ร่างและส่งตรวจได้ แต่เผยแพร่ ตั้งเวลาเผยแพร่ แก้บทความ Published โดยตรง เปลี่ยนสิทธิ์ผู้ใช้ หรืออนุมัติ VIP ไม่ได้; Admin และ Owner เท่านั้นที่อนุมัติและเผยแพร่ Owner มอบหมายบทบาทที่มีอยู่ได้ แต่เพิ่มสิทธิ์เผยแพร่ให้ Editor เป็นรายบุคคลไม่ได้ หากแก้เนื้อหาที่เผยแพร่แล้ว Editor ต้องส่ง revision รอตรวจ โดยฉบับเดิมแสดงต่อจน Admin/Owner อนุมัติฉบับใหม่

### 3.2 ระดับการอ่านเนื้อหา

| ระดับที่ตั้งไว้ | Guest | Member | VIP ที่ยังใช้ได้ |
|---|---|---|---|
| Public | อนุญาต | อนุญาต | อนุญาต |
| Member | ให้เข้าสู่ระบบ/สมัคร | อนุญาต | อนุญาต |
| VIP | แสดงวิธีขอ VIP | แสดงวิธีขอ VIP | อนุญาต |

ตารางนี้ใช้กับ `read_access` ของข้อความบทความและแบบทดสอบ ไม่ได้อนุญาตให้ Guest ดาวน์โหลดไฟล์

### 3.3 ระดับการดาวน์โหลดไฟล์ — ต้องล็อกอินทุกระดับ

| `download_access` ของไฟล์ | Guest | Member ที่ยืนยันตัวตนและล็อกอิน | VIP ที่ยืนยันตัวตน ล็อกอิน และยังไม่หมดอายุ |
|---|---|---|---|
| Member | ให้ล็อกอิน/สมัครก่อน | อนุญาต | อนุญาต |
| VIP | ให้ล็อกอิน/สมัครก่อน แล้วตรวจ VIP | แสดงวิธีขอ VIP | อนุญาต |

- ตั้ง `read_access` สำหรับเนื้อหาเป็น Public/Member/VIP และ `download_access` แยกรายไฟล์เป็น Member/VIP เท่านั้น ไม่มีตัวเลือกดาวน์โหลด Public
- ไฟล์แนบเนื้อหา Public หรือ Member ใช้ Member เป็นค่าเริ่มต้น ส่วนเนื้อหา VIP ใช้ VIP เป็นค่าเริ่มต้น ผู้ดูแลเปลี่ยนระดับไฟล์ได้ แต่ปิดเงื่อนไขล็อกอินไม่ได้
- ตัวอย่าง: บทความอ่านได้ Public แต่ไฟล์แนบ A และ B ต้องเป็นสมาชิกที่ล็อกอิน ส่วนไฟล์ C ต้องเป็น VIP ที่ล็อกอิน
- เมื่อตั้งเนื้อหาเป็น VIP แต่ไฟล์แนบเป็น Member ระบบต้องแสดงผลกระทบให้ผู้ดูแลเห็นชัดเจน เพราะสมาชิกทั่วไปที่ล็อกอินจะดาวน์โหลดไฟล์นั้นผ่านหน้าข้อมูลตัวอย่างได้
- รายการ Published สามารถแสดงชื่อ หมวด และบทสรุปสาธารณะที่ผู้ดูแลเขียนแยกไว้ ห้ามตัดบทสรุปจากเนื้อหาลับมาแสดงอัตโนมัติ
- ร่าง รายการรอตรวจ รายการตั้งเวลา และรายการเก็บถาวรต้องไม่ปรากฏบนหน้าสาธารณะ ผลค้นหา หรือ sitemap
- เมื่อ VIP หมดอายุหรือถูกยกเลิก สมาชิกกลับไปใช้สิทธิ์ Member โดยยังเก็บบัญชีและประวัติไว้ ส่วนการระงับบัญชีต้องเพิกถอนทุก session/token ทันที ปฏิเสธการล็อกอินทุกช่องทางและทุกคำขอที่ใช้ session เก่า ผู้ใช้ยังเข้าชมหน้า Public ในฐานะ Guest ได้ แต่ไม่มีสิทธิ์ Member/VIP ตาม FR-05
- การอ่านข้อความบทความใช้ `read_access` ส่วนการดู PDF/ไฟล์แนบตัวอย่าง ดาวน์โหลด และเรียกข้อมูลไฟล์ผ่าน API ใช้ `download_access` เดียวกันและบังคับล็อกอิน เพื่อไม่ให้การดูตัวอย่างข้ามเงื่อนไขดาวน์โหลด
- รูปปก ไอคอน โลโก้ แบนเนอร์ และภาพประกอบที่ตั้งใจเผยแพร่ในบทความสาธารณะแสดงต่อ Guest ได้ตามปกติ ไฟล์เอกสารหรือภาพที่แนบเพื่อดาวน์โหลดต้องเก็บแยกและตรวจสิทธิ์ ห้ามใช้ไฟล์แนบที่จำกัดสิทธิ์เป็นภาพสาธารณะ
- หน้าแสดงเนื้อหาที่จำกัดสิทธิ์ต้องไม่ส่งเนื้อหาเต็มหรือเฉลยที่ยังห้ามดูไปใน HTML, JSON หรือข้อมูลที่ซ่อนไว้ในเบราว์เซอร์

## 4. ข้อกำหนดการทำงาน

### FR-01 — จัดการบทความและเนื้อหา CMS

- สร้าง อ่าน แก้ไข ย้ายเข้าถังขยะ และกู้คืนเนื้อหาได้ การลบถาวรให้เฉพาะผู้มีสิทธิ์และต้องยืนยัน
- รองรับบทความ เอกสารความรู้ ข่าวประกาศ และเอกสารประชาสัมพันธ์
- มีช่องชื่อเรื่อง URL slug บทสรุป เนื้อหาแบบ Rich Text รูปปก หมวด แท็ก ภาษา ผู้เขียน และวันที่เผยแพร่
- CMS จัดการคำแปลลาวและอังกฤษเป็นคู่เนื้อหาเดียวกันได้ โดยแยกชื่อ บทสรุป เนื้อหา slug SEO และสถานะเผยแพร่ต่อภาษา พร้อมแสดงว่ารายการใดยังขาดคำแปล
- แนบหลายไฟล์ในหนึ่งรายการและเรียงลำดับได้
- Rich Text รองรับหัวข้อ รายการ ตาราง ลิงก์ และรูปภาพ พร้อมคำอธิบายภาพและข้อความทดแทน
- สถานะงาน: Draft → Pending Review → Scheduled/Published → Archived และส่งกลับแก้ไขพร้อมหมายเหตุได้
- การเปลี่ยนเป็น Scheduled/Published ทำได้เฉพาะ Admin/Owner และตรวจสิทธิ์ที่เซิร์ฟเวอร์ แม้เรียก API ตรง; Editor ส่ง revision รอตรวจตามหัวข้อ 3.1
- ลิงก์ดูตัวอย่างร่าง/revision ต้องล็อกอินด้วยบัญชีทีมงานที่มีสิทธิ์และใช้ URL ตามหัวข้อ 5.5 รุ่นแรกไม่ออกลิงก์ร่างสาธารณะหรือ signed link ที่อ่านได้โดยไม่ล็อกอิน พร้อมเก็บประวัติการแก้ไขและผู้ดำเนินการ
- สำหรับเนื้อหากฎหมาย/ภาษี มีช่องประเทศหรือเขตอำนาจ หน่วยงานผู้ออก เลขที่เอกสาร วันที่ออก วันที่มีผล วันที่ทบทวนล่าสุด และลิงก์แหล่งต้นฉบับ
- ระบุเอกสารที่ถูกแทนที่หรือยกเลิกแล้ว และเชื่อมไปยังฉบับใหม่ เพื่อให้ผู้อ่านทราบสถานะข้อมูล
- มีช่องคำเตือนสำหรับเนื้อหาบัญชี ภาษี อากร และกฎหมาย โดยตั้งต้นว่า “ข้อมูลนี้เป็นความรู้ทั่วไป โปรดตรวจสอบฉบับทางการและข้อมูลที่มีผลใช้บังคับก่อนนำไปใช้” แสดงคำเตือนภาษาลาว/อังกฤษที่ตรวจทานแล้วพร้อมหน่วยงานผู้ออก วันที่มีผล และแหล่งต้นฉบับ หากข้อมูลใดไม่ทราบให้ระบุว่าไม่ทราบ ไม่สร้างค่าอ้างอิงขึ้นเอง
- งานตั้งเวลาใช้เขตเวลาเว็บไซต์ที่ผู้ดูแลตั้งไว้ เสนอเริ่มต้น `Asia/Vientiane` หากกลุ่มหลักอยู่ในลาว

### FR-02 — อัปโหลดและจัดการไฟล์

- เริ่มต้นรองรับ PDF, JPG, JPEG, PNG, WebP, DOCX, XLSX และ PPTX
- คำว่า “ไฟล์ใดก็ได้” หมายถึงชนิดที่เจ้าของอนุญาตในรายการชนิดไฟล์ ไม่เปิดรับ executable, script หรือ HTML ที่ทำงานได้โดยอัตโนมัติ
- ค่าเสนอ: เอกสารไม่เกิน 50 MB/ไฟล์ รูปภาพไม่เกิน 10 MB/ไฟล์ ปรับได้ตามข้อจำกัดโฮสติ้ง
- ตรวจนามสกุล MIME และชนิดข้อมูลจริงของไฟล์ พร้อมแสดงความคืบหน้าและข้อความผิดพลาดที่เข้าใจง่าย
- แสดงชื่อไฟล์ ชนิด ขนาด ภาษา รุ่น วันที่อัปโหลด และสิทธิ์ดาวน์โหลด
- มี Media Library ค้นหาและนำไฟล์เดิมกลับมาใช้ได้ ก่อนลบต้องแจ้งรายการที่กำลังใช้งานไฟล์นั้น
- ไฟล์เอกสารและไฟล์แนบสำหรับดาวน์โหลดทุกประเภทอยู่ในพื้นที่จัดเก็บ private; เฉพาะภาพปก/ภาพประกอบ/ภาพประชาสัมพันธ์ที่ตั้งใจเปิดเผยจึงใช้พื้นที่ public
- สแกนทุกไฟล์ที่อัปโหลด รวมเอกสาร ภาพประกอบ ภาพปก และแบนเนอร์ ก่อนเปิดเผยหรือดาวน์โหลด ใช้สถานะ Quarantined/Pending → Clean หรือ Rejected/Error; เฉพาะ Clean เท่านั้นที่ใช้ได้ หาก scanner ล่ม/timeout ให้กักไฟล์ไว้และแจ้งทีมงาน ห้ามเปิดอัตโนมัติหรือให้กดข้ามผลสแกน
- ภาพอัปโหลดต้องลบ EXIF/ข้อมูลตำแหน่งก่อนเผยแพร่ โดยตรวจชนิดไฟล์และสแกนทั้งไฟล์ต้นฉบับกับผลแปลงที่จะส่งให้ผู้ใช้ ไฟล์ต้นฉบับที่ยังมี metadata ไม่เปิดผ่าน URL สาธารณะ
- การแทนที่ไฟล์ต้องไม่ทำให้ประวัติเอกสารหรือการอ้างอิงรุ่นเก่าหายไปโดยไม่แจ้งผู้ดูแล
- PDF ที่เป็นข้อความให้เปิดอ่านในเว็บได้หลังล็อกอินและผ่านสิทธิ์ไฟล์ ส่วน DOCX/XLSX/PPTX รองรับดาวน์โหลดก่อน ไม่รวมการแสดงตัวอย่างออนไลน์ในรุ่นเริ่มต้น

### FR-03 — ดูเอกสารและดาวน์โหลด

- หน้ารายละเอียดและ metadata เอกสารเข้าชมได้ตามสิทธิ์เนื้อหา โดยแสดงบทสรุป ข้อมูลรุ่น/วันที่มีผล รายการไฟล์ และป้าย Member/VIP สำหรับดาวน์โหลด
- Guest กดดาวน์โหลดไฟล์ใด ๆ จะพบข้อความ “กรุณาเข้าสู่ระบบก่อนดาวน์โหลด” พร้อมตัวเลือกอีเมล เบอร์โทรศัพท์ และ Google โดยไม่บังคับล็อกอินขณะเข้าชมหน้าสาธารณะ
- หลังเข้าสู่ระบบสำเร็จให้กลับไปหน้าเอกสารและไฟล์ที่เลือกไว้ในภาษาเดิม พร้อมตรวจสิทธิ์ใหม่ หากเป็นไฟล์ Member ให้กดดาวน์โหลดต่อได้ หากยังไม่มี VIP ให้แสดงวิธีขอ VIP
- ผู้ที่ยังไม่ยืนยันช่องทางสมัครได้รับขั้นตอนยืนยันก่อนดาวน์โหลด ส่วนผู้ไม่มีสิทธิ์ VIP ได้รับข้อความและช่องทางขอ VIP
- ตรวจสอบการล็อกอิน การยืนยันตัวตน สถานะเผยแพร่ สิทธิ์ไฟล์ บัญชี และอายุ VIP ที่เซิร์ฟเวอร์ก่อนส่งไฟล์ทุกครั้ง
- บันทึกคำขอดาวน์โหลดที่ได้รับอนุญาต โดยไม่ตีความจำนวนคำขอว่าเป็นจำนวนดาวน์โหลดสำเร็จแน่นอน
- ไฟล์แนบทุกระดับส่งผ่าน endpoint ที่ตรวจล็อกอินและสิทธิ์ทุกคำขอ รวม URL ตรง API, thumbnail/preview ที่สร้างจากไฟล์ และคำขอแบบ Range ของ PDF
- ไฟล์ดาวน์โหลด/preview และหน้าร่างส่ง `Cache-Control: private, no-store` และ `X-Content-Type-Options: nosniff` พร้อม Content-Type ที่ตรวจแล้ว; ไฟล์ดาวน์โหลดใช้ `Content-Disposition: attachment` ส่วน PDF preview ใช้ inline หลังผ่านสิทธิ์ ห้าม CDN/service worker cache ไฟล์หรือหน้าส่วนตัวเป็นสาธารณะ
- หากปรับใช้ลิงก์ signed URL ในอนาคต ต้องกำหนดอายุสั้นและยอมรับว่าลิงก์ที่ออกแล้วอาจยังใช้ได้จนหมดอายุ จึงไม่ใช้กับกรณีที่ต้องตัดสิทธิ์ทันที ดูข้อจำกัดใน [เอกสาร Amazon S3 presigned URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)
- ห้ามใช้ URL จัดเก็บไฟล์แนบแบบ public ถาวร; `robots.txt` และ `noindex` ไม่ใช่กลไกตรวจสิทธิ์
- เมื่อผู้ใช้ดาวน์โหลดไฟล์ไปแล้ว ระบบไม่สามารถเรียกคืนสำเนาบนอุปกรณ์ผู้ใช้ได้

### FR-04 — ค้นหาและกรองข้อมูลภายในเว็บไซต์

- มีช่องค้นหาหลักหนึ่งจุดที่เห็นชัดบนหน้าแรก ส่วนหน้าอื่นเข้าถึงการค้นหาผ่านส่วนหัวได้โดยไม่แสดงช่องค้นหาซ้ำในหน้าจอเดียว รองรับข้อความลาว อังกฤษ และเลขที่เอกสาร โดยค่าเริ่มต้นค้นในภาษาที่เลือกและสามารถเปลี่ยนเป็นทุกภาษาได้
- ค้นจากชื่อเรื่อง บทสรุปที่เปิดเผย แท็ก หมวด และเลขที่เอกสาร โดยให้ชื่อและเลขเอกสารมีน้ำหนักสูง
- กรองตามหมวด ชนิดเนื้อหา ชนิดไฟล์ ภาษา ปี และระดับการอ่าน Public/Member/VIP หรือสิทธิ์ไฟล์ Member/VIP ได้
- เรียงตามความเกี่ยวข้อง ล่าสุด และยอดดาวน์โหลดได้ พร้อมแบ่งหน้าและเก็บเงื่อนไขค้นหาไว้ใน URL
- ผลลัพธ์แสดงชื่อ หมวด บทสรุป วันที่ รุ่น ชนิดไฟล์ และป้ายสิทธิ์
- เมื่อไม่มีผลลัพธ์ แนะนำให้เปลี่ยนคำค้นหรือล้างตัวกรอง
- รุ่นเริ่มต้นค้นจาก metadata และข้อความบทความที่ผู้ใช้มีสิทธิ์อ่าน ไม่รับรองการค้นข้อความภายใน PDF/ภาพสแกน
- ชื่อและบทสรุปสาธารณะของเนื้อหา VIP ค้นพบได้ แต่ข้อความในเนื้อหาหรือไฟล์ VIP ต้องไม่ถูกนำมาแสดงเป็น snippet แก่ผู้ไม่มีสิทธิ์
- ใช้ชุดคำค้นลาวและอังกฤษจริงทดสอบ รวมข้อความลาวที่ไม่มีการเว้นวรรคและภาษาอังกฤษที่ใช้ตัวพิมพ์ใหญ่/เล็ก แนะนำเริ่มจาก substring search และประเมินดัชนี trigram ก่อนใช้จริง โดย PostgreSQL มี `pg_trgm` สำหรับ similarity และดัชนีค้นข้อความ ดู [เอกสาร PostgreSQL](https://www.postgresql.org/docs/current/pgtrgm.html)

### FR-05 — สมัครสมาชิก เข้าสู่ระบบ และ VIP

- รองรับ 3 ช่องทางตั้งแต่รุ่นแรก: อีเมล เบอร์โทรศัพท์ และ Google โดยทุกช่องทางสมัครใหม่ได้ระดับ Member เท่ากัน ไม่ได้รับ VIP อัตโนมัติ
- **อีเมล:** สมัครด้วยชื่อ อีเมล และรหัสผ่าน ยืนยันอีเมลผ่านลิงก์ก่อนดาวน์โหลด เข้าสู่ระบบด้วยอีเมล/รหัสผ่าน และกู้รหัสผ่านทางอีเมลได้
- **เบอร์โทรศัพท์:** เลือกรหัสประเทศ กรอกเบอร์และชื่อ ยืนยัน OTP ทาง SMS เพื่อสมัครหรือเข้าสู่ระบบได้โดยไม่ต้องมีอีเมลหรือรหัสผ่าน เก็บเบอร์ในรูปแบบ E.164 และรองรับรหัสประเทศลาว `+856`
- OTP มีอายุ 5 นาที ใช้ครั้งเดียว ส่งใหม่ได้หลัง 60 วินาที ลองได้ไม่เกิน 5 ครั้งต่อ challenge และทำให้รหัสเดิมใช้ไม่ได้เมื่อออกรหัสใหม่ ผู้ให้บริการ SMS ต้องทดสอบส่งถึงเครือข่ายในลาวจริงก่อนเปิดใช้
- ก่อนส่ง SMS ต้องผ่านการตรวจบอตที่ตรวจผลบนเซิร์ฟเวอร์ พร้อม rate limit เสนอเริ่มต้นไม่เกิน 5 ครั้ง/เบอร์/ชั่วโมง, 10 ครั้ง/เบอร์/วัน และ 20 ครั้ง/IP/ชั่วโมง นับรวมการส่งซ้ำ และใช้รูปแบบเบอร์ที่ normalize แล้วเพื่อป้องกันหลบโควตา
- มีเพดาน SMS ทั้งจำนวนและงบเงินจริงรายวันตามเขตเวลาเว็บไซต์ ค่าเสนอจำนวนเริ่มต้น 100 SMS segments/วัน (นับส่วนข้อความที่คิดเงินจริง รวมข้อความที่แบ่งหลายส่วน) ส่วนวงเงินและสกุลเงินให้ Owner ตั้งตามผู้ให้บริการก่อนเปิดจริง หากยังไม่ตั้งวงเงินให้ปิด SMS ไว้ แสดงยอดใช้และแจ้งเตือนที่ 80% ของเพดาน
- จองโควตา/งบแบบ atomic ก่อนเรียกผู้ให้บริการโดยคิดจำนวน segment และต้นทุนสูงสุดที่ประเมินได้ และตั้ง spending cap ฝั่งผู้ให้บริการเมื่อรองรับ เพื่อไม่ให้คำขอพร้อมกันส่งเกินเพดาน ห้ามรีเซ็ตงบจากการ restart แอป
- หากไม่ผ่านการตรวจบอต เกิน rate limit/งบ หรือส่ง SMS ไม่สำเร็จ ให้หยุดคำขอนั้นและไม่สร้าง authenticated session; ไม่มีการ retry ส่งที่เสียเงินโดยอัตโนมัติไม่จำกัด ผู้ใช้เลือกช่องทางอื่นที่เชื่อมไว้ได้ การขอ OTP ใหม่ไม่ได้ล็อกเอาต์ session เดิมที่ยังถูกต้อง
- **Google:** มีปุ่ม “Continue with Google” สำหรับสมัครหรือเข้าสู่ระบบ หากยังไม่มีบัญชีให้สร้าง Member หลังยืนยันกับ Google สำเร็จ ไม่ขอให้ตั้งรหัสผ่านของเว็บไซต์และไม่ขอรหัสผ่าน Google
- เชื่อม Google ผ่าน OAuth/OIDC ฝั่งเซิร์ฟเวอร์ โดยใช้รหัสบัญชี Google (`sub`) เป็นตัวระบุถาวรตาม [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect) พร้อมตรวจ callback/state และข้อมูลยืนยันจากผู้ให้บริการ ไม่เชื่อค่าระบุตัวตนที่ส่งจากเบราว์เซอร์โดยตรง
- บัญชีต้องมีอย่างน้อยหนึ่งช่องทางที่ยืนยันแล้วก่อนดาวน์โหลด: อีเมลที่ยืนยัน เบอร์โทรที่ผ่าน OTP หรือ Google identity ที่ยืนยันแล้ว
- ผู้ใช้เพิ่มและเชื่อมช่องทางอื่นกับบัญชีเดิมได้หลังยืนยันตัวตนซ้ำและพิสูจน์การครอบครองช่องทางใหม่ ห้ามรวมบัญชีหรือโอนสิทธิ์เพียงเพราะอีเมล/เบอร์ที่กรอกตรงกัน
- ถ้า Google login ใช้อีเมลที่ตรงกับบัญชีเดิมแต่ยังไม่ได้เชื่อม ให้เข้าสู่ขั้นตอนยืนยันบัญชีเดิมและเชื่อมอย่างชัดเจนก่อน ห้ามสร้างบัญชีซ้ำหรือรวมบัญชีอัตโนมัติ และไม่เปิดเผยข้อมูลบัญชีเดิมต่อผู้ที่ยังไม่พิสูจน์ตัวตน
- การเปลี่ยนอีเมล/เบอร์โทรต้องยืนยันช่องทางใหม่ การยกเลิกการเชื่อมต้องเหลือวิธีล็อกอินที่ยืนยันแล้วอย่างน้อยหนึ่งวิธี และต้องมีการตรวจสอบก่อนทำรายการ
- สมาชิกแก้ไขข้อมูลส่วนตัว จัดการวิธีล็อกอิน เปลี่ยนรหัสผ่านเมื่อมีบัญชีแบบรหัสผ่าน ออกจากระบบ และดูระดับสมาชิก/วันหมดอายุของตนเองได้
- บัญชีที่มีเฉพาะเบอร์โทรหรือ Google ไม่ถูกบังคับยืนยันอีเมลที่ไม่มี และต้องใช้ช่องทางที่ยืนยันจริงสำหรับแจ้งเตือน/กู้บัญชี ถ้าไม่มีวิธีกู้คืนที่ใช้ได้ให้มีขั้นตอนติดต่อผู้ดูแลโดยไม่ให้สิทธิ์จากคำอ้างเพียงอย่างเดียว
- กรณี OTP ส่งไม่สำเร็จ Google ถูกยกเลิก หรือบริการภายนอกไม่พร้อม ให้แสดงข้อความลองใหม่/เลือกช่องทางที่เชื่อมไว้ ไม่สร้าง session หรือบัญชีที่ยังยืนยันไม่สำเร็จ
- หน้าสมัคร ส่ง OTP ยืนยันอีเมล และกู้รหัสผ่านตอบข้อความ สถานะ HTTP และโครงสร้าง response เหมือนกัน ไม่ว่าอีเมล/เบอร์นั้นมีบัญชีแล้วหรือไม่ เช่น “หากข้อมูลนี้สามารถใช้ดำเนินการได้ ระบบจะส่งขั้นตอนให้” ไม่เปิดเผยสถานะบัญชีผ่านเวลาตอบที่แตกต่างอย่างชัดเจน และส่งรายละเอียดเฉพาะช่องทางที่ผู้ใช้พิสูจน์การครอบครองแล้ว
- Admin/Owner อนุมัติ ต่ออายุ หรือยกเลิก VIP พร้อมระบุวันเริ่ม วันสิ้นสุด และหมายเหตุได้ การระงับบัญชีเป็นอีกสถานะแยกจากการยกเลิก VIP
- ตรวจอายุสิทธิ์จากเวลาปัจจุบันทุกคำขอ แม้งานแจ้งเตือนตามเวลาจะยังไม่ทำงาน
- ผู้ใช้หนึ่งคนมีสมาชิกภาพปัจจุบันได้หนึ่งรายการ โดยสมัครสำเร็จสร้าง Member ทันที (การดาวน์โหลดยังต้องยืนยันตัวตนตามช่องทาง) VIP เริ่มใช้ได้เฉพาะหลัง Admin/Owner อนุมัติและอยู่ในช่วงเวลาใช้งาน
- ใช้ `memberships.is_current` ระบุแถวปัจจุบันและบังคับ unique ต่อ user ที่ฐานข้อมูล แยก `status` ของแถวและช่วงเวลาเริ่ม/สิ้นสุดออกจาก flag นี้ เมื่ออนุมัติ/ต่ออายุ/ยกเลิก/หมดอายุ ให้ปิดแถวเก่าเป็นประวัติและสร้างแถวปัจจุบันใน transaction เดียว ห้ามมีรายการปัจจุบันหรือช่วงสิทธิ์ที่ใช้งานทับซ้อนกัน
- ถึงแม้งานแปลง VIP ที่หมดอายุเป็นแถว Member ยังไม่ทำงาน ระบบตรวจเวลาจริงและให้สิทธิ์เพียง Member; แถว VIP ที่หมดอายุไม่ถือว่า active การระงับบัญชีปิดกั้นทุกระดับโดยไม่ลบประวัติสมาชิกภาพ
- เก็บประวัติการเปลี่ยนระดับสมาชิกพร้อมผู้ดำเนินการ เวลา และหมายเหตุ แถวประวัติไม่ถูกนำกลับมาเป็นสิทธิ์ปัจจุบันโดยการแก้ flag ผ่านหน้าฟอร์มทั่วไป
- เมื่อ Admin/Owner ระงับบัญชี ให้เพิกถอนทุก session, remember-me token และ token ที่เข้าถึงไฟล์ทันที พร้อมตรวจสถานะจากเซิร์ฟเวอร์ทุกคำขอ ผู้ใช้ล็อกอินใหม่ด้วยอีเมล OTP หรือ Google ไม่ได้ และ session เก่าใช้ต่อไม่ได้
- หลังระงับยังเปิดหน้า Public แบบ Guest ได้ ไฟล์ที่ส่งไปก่อนหน้าหรือการถ่ายโอนที่เริ่มก่อนระงับเรียกคืนไม่ได้ แต่คำขอถัดไป รวม Range request ใหม่ ต้องปฏิเสธ การเปิดบัญชีคืนไม่คืน session เดิมและไม่ต่ออายุ VIP อัตโนมัติ ต้องล็อกอินใหม่และตรวจสิทธิ์ปัจจุบัน
- สมาชิกบันทึกบทความโปรด ดูประวัติคำขอดาวน์โหลด และผลแบบทดสอบของตนเองได้
- ห้ามสมาชิกแก้ระดับตนเองหรือเปิดดูข้อมูล/ประวัติของสมาชิกคนอื่น
- มีหน้าสิทธิประโยชน์ VIP และช่องทางติดต่อเจ้าของ รุ่นเริ่มต้นไม่แสดงปุ่มชำระเงินที่ยังใช้ไม่ได้

### FR-06 — คำถาม คำตอบ และแบบทดสอบ

- แยก FAQ สำหรับอ่านความรู้ ออกจากแบบทดสอบที่ต้องส่งคำตอบและตรวจคะแนน
- ผู้ดูแลสร้างคลังคำถาม ชุดแบบทดสอบ หมวด ระดับความยาก และระดับสิทธิ์ Public/Member/VIP ได้
- รุ่นเริ่มต้นมีคำถามแบบเลือกคำตอบเดียวและถูก/ผิด พร้อมตัวเลือก คำตอบที่ถูก คำอธิบาย และลิงก์บทความอ้างอิง
- กำหนดจำนวนครั้งที่ทำได้ สุ่มลำดับคำถาม/ตัวเลือก คะแนนผ่าน และเวลาได้ โดยค่าเริ่มต้นเป็นแบบฝึกไม่จับเวลาและทำซ้ำได้
- ค่าเริ่มต้นทุกข้อมี 1 คะแนน คำตอบผิดหรือไม่ตอบเป็น 0 คะแนน ไม่มีคะแนนติดลบ
- แสดงจำนวนข้อ ความคืบหน้า และผลคะแนนเป็นจำนวนข้อถูกและเปอร์เซ็นต์ พร้อมผลผ่าน/ไม่ผ่าน
- ฝั่งเซิร์ฟเวอร์ตรวจคะแนนและจำนวนครั้งที่ทำ ห้ามส่งเฉลยไปก่อนส่งแบบทดสอบสำเร็จ
- ให้ดูเฉลยและคำอธิบายหลังส่งตามการตั้งค่า มีการป้องกันการส่งซ้ำจนเกิดผลสอบหลายรายการ
- สมาชิกดูประวัติของตนเองได้ Guest ทำแบบฝึก Public ได้โดยไม่เก็บประวัติถาวร และไม่ใช้ข้อจำกัดจำนวนครั้งแบบยืนยันตัวบุคคลกับ Guest
- เมื่อแก้ชุดข้อสอบ ต้องเก็บรุ่นคำถามและเกณฑ์ที่ใช้ในครั้งที่ทำ เพื่อไม่ให้ผลคะแนนเก่าเปลี่ยนตามการแก้ไข
- ถ้าเปิดจับเวลา ระบบยึดเวลาเซิร์ฟเวอร์และมีข้อความชัดเจนเมื่อหมดเวลา

### FR-07 — หมวดหมู่และการนำทาง

- มีหมวดเริ่มต้นตามหัวข้อ 1.1 เพิ่มหมวดใหม่ได้โดยระบบไม่กำหนดเพดานจำนวนหมวดตายตัว รองรับหมวดย่อยและแท็กหลายรายการ
- Owner/Admin จัดการ CRUD หมวดและหมวดย่อยผ่านหลังบ้านได้ ส่วน Editor เลือกใช้หมวดที่มีอยู่ได้ แต่แก้โครงสร้างหมวดไม่ได้ตามบทบาทคงที่ของรุ่นแรก
- รุ่นแรกจำกัด 2 ระดับ: หมวดหลักและหมวดย่อยหนึ่งชั้น หมวดย่อยมีลูกไม่ได้ เมื่อย้ายหมวดต้องตรวจทั้งตัวมันและลูกว่าจะไม่เกินความลึกนี้
- Create: เพิ่มหมวดหลักหรือหมวดย่อย พร้อมชื่อ คำอธิบาย slug และ SEO แยกภาษาลาว/อังกฤษ รวมไอคอน/รูปภาพ ลำดับแสดง และสถานะเปิดใช้งาน
- Read: ดูรายการและรายละเอียดหมวด พร้อมค้นหา กรองตามสถานะ/หมวดแม่ และแสดงจำนวนเนื้อหาที่เชื่อมโยง
- Update: แก้ข้อมูล คำแปล หมวดแม่ ลำดับ และสถานะได้ ห้ามเลือกตัวเองหรือลูกหลานเป็นหมวดแม่เพื่อป้องกันโครงสร้างวนซ้ำ
- Delete: ย้ายหมวดว่างเข้าถังขยะและกู้คืนได้ หากมีเนื้อหา แบบทดสอบ FAQ หรือหมวดย่อยที่ยังใช้งาน ต้องย้ายความสัมพันธ์เหล่านั้นไปยังหมวดอื่นก่อน ห้ามลบข้อมูลที่เกี่ยวข้องตามหมวดโดยอัตโนมัติ
- การลบถาวรให้เฉพาะ Owner หลังยืนยัน และทำได้เมื่อไม่มีความสัมพันธ์ค้างอยู่ ส่วนการลบ/กู้คืนและการแก้ข้อมูลสำคัญต้องมี Audit Log
- เมื่อปิดใช้งานหมวด ให้ซ่อนจากเมนู ตัวกรอง และ sitemap สาธารณะ พร้อมหยุดแสดงหน้าหมวด; สถานะบทความและสิทธิ์ดาวน์โหลดไฟล์ยังเป็นไปตามค่าของรายการนั้น ผู้ดูแลต้องเห็นผลกระทบก่อนบันทึก
- เมนูหมวดและรายการหมวดหน้าแรกอ่านจากฐานข้อมูลตามสถานะ ลำดับ และคำแปลที่เผยแพร่ ไม่เขียนรายการ 7 หมวดตายตัวในโค้ด
- แต่ละเนื้อหามีหมวดหลักหนึ่งหมวด และเพิ่มหมวดรองได้ เพื่อกำหนด breadcrumb และ URL หลักชัดเจน
- หน้าหมวดแสดงคำอธิบาย บทความ เอกสาร และแบบทดสอบที่เกี่ยวข้อง พร้อมตัวกรอง
- มี breadcrumb และรายการเนื้อหาที่เกี่ยวข้อง
- หากเปลี่ยน slug ที่เผยแพร่แล้ว ต้อง redirect จาก URL เก่า และไม่ให้หมวดหลายเส้นทางสร้างหน้าเนื้อหาซ้ำ ใช้ namespace และกฎ slug ตามหัวข้อ 5.5

### FR-08 — การค้นพบผ่าน Google และ AI ภายนอก

- หน้าแรก หน้าหมวด และหน้าเนื้อหาเผยแพร่มี HTML ที่อ่านสาระสำคัญได้ตั้งแต่ตอบกลับจากเซิร์ฟเวอร์
- ตั้ง title, meta description, canonical, Open Graph และข้อความทดแทนรูปภาพได้
- มี sitemap เฉพาะ URL สาธารณะที่เผยแพร่ และ `robots.txt` ที่กำหนดอย่างเหมาะสม
- ใช้ structured data ให้ตรงชนิดเนื้อหา เช่น Article, BreadcrumbList และ Organization โดยข้อมูลต้องตรงกับสิ่งที่แสดงจริง
- หน้าข้อมูลตัวอย่างของเนื้อหาจำกัดสิทธิ์แสดงเฉพาะชื่อและบทสรุปสาธารณะ ไม่เปิดเอกสารหรือไฟล์แนบ Member/VIP ให้ crawler และไม่ใส่ URL ดาวน์โหลด/preview ใน sitemap; หน้ารายละเอียดเอกสารสาธารณะยังค้นพบได้
- หากอนาคตต้องการให้ Google จัดทำดัชนีเนื้อหาที่อยู่หลัง paywall ให้พิจารณากฎและ markup แยกต่างหากตาม [แนวทาง Google สำหรับเนื้อหาสมาชิก](https://developers.google.com/search/docs/appearance/structured-data/paywalled-content)
- เชื่อม Google Search Console และส่ง sitemap หลังมีโดเมนและเผยแพร่จริง
- เนื้อหามีหัวข้อชัดเจน ผู้เขียน วันที่ปรับปรุง และแหล่งอ้างอิง เพื่อให้คนและระบบค้นหาเข้าใจข้อมูลได้
- Google ระบุว่าไม่ต้องมีการปรับแต่งเฉพาะหรือ schema พิเศษเพื่อปรากฏใน AI features แต่หน้าเว็บยังต้องผ่านข้อกำหนด Search ที่เกี่ยวข้อง การเตรียม SEO ไม่รับประกันการจัดทำดัชนี อันดับ หรือการถูกอ้างอิง ดู [Google AI features and your website](https://developers.google.com/search/docs/appearance/ai-features)
- การรองรับ AI ภายนอกแต่ละบริการขึ้นกับ crawler และนโยบายบริการนั้น ต้องประเมินแยกจาก Google และไม่ใช้เป็นเกณฑ์รับประกันผลส่งมอบ

### FR-09 — บทความประชาสัมพันธ์และโฆษณา

- สร้างบทความประชาสัมพันธ์ รูปแบนเนอร์ และแนบไฟล์เอกสารได้
- ตั้งตำแหน่งแสดง ลำดับ ลิงก์ปลายทาง และวันเริ่ม/สิ้นสุดการแสดงได้
- ตำแหน่งที่เลือกใช้ได้: ช่วงท้ายหน้าแรก ช่วงท้ายบทความ และช่วงท้ายหน้าหมวด โดยมีตัวอย่างก่อนเผยแพร่ หน้าแต่ละหน้ามีพื้นที่ประชาสัมพันธ์ที่แสดงพร้อมกันไม่เกินหนึ่งตำแหน่ง และหากไม่มีรายการให้ซ่อนพื้นที่นั้น
- แสดงป้าย “โฆษณา” หรือ “ประชาสัมพันธ์” ให้ชัด และรองรับข้อความทดแทนรูป
- สื่อประชาสัมพันธ์อยู่ในกรอบที่กำหนด ไม่ล้นจอและไม่บังเนื้อหา ไม่มี popup โฆษณา แบนเนอร์ลอยทับเนื้อหา ภาพสลับอัตโนมัติ หรือสื่อเล่นอัตโนมัติในรุ่นแรก
- ขอบเขตงานโฆษณารุ่นแรกเป็นการจัดการสื่อโดยทีมงาน รายการยกเว้นด้านการซื้อขายและการกำหนดเป้าหมายอยู่ในหัวข้อ 1.3

### FR-10 — หลังบ้านและรายงาน

- Dashboard แสดงบทความ เอกสาร สมาชิก VIP ที่ใช้งานได้จากสมาชิกภาพปัจจุบัน/ช่วงเวลาจริงและบัญชีไม่ถูกระงับ เนื้อหารอตรวจ และคำขอดาวน์โหลดที่อนุญาต
- รายการจัดการมีช่องค้นหา ตัวกรอง สถานะ และปุ่มทำงานตามสิทธิ์ทีมงาน
- รายงานเนื้อหายอดนิยม คำค้นที่ไม่พบผลลัพธ์ การดาวน์โหลดแยกไฟล์ และผลแบบทดสอบแบบสรุป
- ส่งออกรายงาน CSV ได้ตามสิทธิ์ โดยป้องกันช่องข้อความจากผู้ใช้ที่ขึ้นต้นด้วย `=`, `+`, `-`, `@` รวมหลังช่องว่าง/tab ไม่ให้ทำงานเป็นสูตรเมื่อเปิดใน spreadsheet ใช้วิธี escape ที่ทดสอบกับโปรแกรมเป้าหมายและคงค่าข้อมูลต้นฉบับในฐานข้อมูล
- ตั้งชื่อเว็บไซต์ โลโก้ ช่องทางติดต่อ เมนู ส่วนท้าย SEO เริ่มต้น ชนิดไฟล์ และเขตเวลาได้
- ค่าติดต่อเริ่มต้นใช้ข้อมูลในหัวข้อ 1.4: contact_email, whatsapp_number, facebook_url และ tiktok_url ตรวจรูปแบบอีเมล/เบอร์/HTTPS URL ก่อนบันทึก และใช้ค่าตั้งส่วนกลางกับหน้าติดต่อ ส่วนท้าย และช่องทางขอ VIP
- มี Audit Log แบบ append-only สำหรับการเผยแพร่ ลบ แก้สิทธิ์ไฟล์ เปลี่ยนสมาชิก ระงับบัญชี เปลี่ยนบทบาท และกู้คืน 2FA โดยบันทึกผู้ดำเนินการ เวลา เป้าหมาย และผลการทำรายการ; ไม่มีหน้าจอ/API แก้หรือลบ log แม้เป็น Owner และกำหนดสิทธิ์ฐานข้อมูลของแอปไม่ให้ UPDATE/DELETE log ตาม NFR-04

## 5. แนวทางออกแบบ UI/UX ตามภาพอ้างอิง

### 5.1 บุคลิกและองค์ประกอบภาพ

ยึดโลโก้ **BAN BUNSI** ที่เจ้าของส่งมาเป็นแนวทางแบรนด์ล่าสุด ใช้น้ำเงิน–ขาวเป็นธีมเริ่มต้น พื้นที่ส่วนใหญ่เป็นสีขาว ใช้สีน้ำเงินเน้นจุดสำคัญ หน้าตาเรียบง่าย เป็นระเบียบ และไม่แน่นจนรบกวนการอ่าน โครงจากภาพเว็บไซต์เดิมใช้เป็นแนวทางการค้นหาและจัดหมวด โดยรายละเอียดการออกแบบให้ยึดข้อกำหนดฉบับนี้

| องค์ประกอบ | แนวทางเสนอ |
|---|---|
| โลโก้ | ใช้โลโก้ BAN BUNSI ต้นฉบับ รักษาสัดส่วน ตัวอักษร และสี ไม่วาดใหม่หรือยืดภาพ; ความสูงเสนอ 48 px บนเดสก์ท็อปและ 40 px บนมือถือ พร้อมพื้นที่ว่างรอบโลโก้ |

โหลด Phetsarath ผ่าน Google Fonts ด้วย `display=swap` และ preconnect ไปยัง `fonts.googleapis.com` กับ `fonts.gstatic.com` ใช้กับหน้าภาษาลาว (`lang="lo"`) และข้อความลาวที่แทรกในหน้าอังกฤษ รวมถึงหลังบ้านภาษาลาว ใช้ class `phetsarath-regular` และ `phetsarath-bold` เมื่อต้องระบุน้ำหนักโดยตรง และแสดง system fallback ระหว่างโหลดเพื่อให้เนื้อหาอ่านได้ทันที ไม่บังคับความสูงบรรทัดจนสระหรือวรรณยุกต์ถูกตัด

### 5.3 หน้าจอที่ต้องออกแบบ

| หน้า | ส่วนสำคัญ |
|---|---|
| หน้าแรก | โลโก้ แนะนำสั้น ช่องค้นหาหนึ่งจุด หมวดแบบย่อ เอกสาร/บทความล่าสุด และประชาสัมพันธ์ช่วงท้ายเมื่อมี |
| หน้าหมวด/ค้นหา | จำนวนผลลัพธ์ รายการพร้อมป้ายสิทธิ์ และตัวกรองพื้นฐาน; ตัวกรองเพิ่มเติมเปิดเมื่อผู้ใช้ต้องการ |
| รายละเอียดบทความ | breadcrumb ผู้เขียน วันที่ สารบัญ เนื้อหา ไฟล์แนบ และรายการเกี่ยวข้อง |
| รายละเอียดเอกสาร | Guest เห็นเฉพาะชื่อ บทสรุป metadata และรายการไฟล์ที่อนุญาตให้เปิดเผย; ตัวอ่าน PDF และดาวน์โหลดเปิดหลังล็อกอินและผ่านสิทธิ์ของไฟล์นั้นตามหัวข้อ 3.3 |
| คลังแบบทดสอบ | หมวด ความยาก จำนวนข้อ เวลา และระดับสิทธิ์ |
| ทำแบบทดสอบ/ผลลัพธ์ | คำถาม ตัวเลือก ความคืบหน้า ส่งคำตอบ คะแนน และคำอธิบาย |
| สมัคร/เข้าสู่ระบบ/ยืนยันตัวตน/กู้บัญชี | เลือกอีเมล เบอร์โทร+OTP หรือ Google ข้อผิดพลาด และกลับไปหน้าเอกสารที่เลือกในภาษาเดิม |
| บัญชีสมาชิก | โปรไฟล์ ช่องทางล็อกอินที่เชื่อม ระดับ/อายุ VIP รายการโปรด ดาวน์โหลด และประวัติแบบทดสอบ |
| สิทธิประโยชน์ VIP | รายละเอียดสิทธิ์ เงื่อนไข และช่องทางติดต่อ |
| เกี่ยวกับเรา/ติดต่อ/นโยบาย | ข้อมูลองค์กร Email/WhatsApp/Facebook/TikTok ตามหัวข้อ 1.4 และนโยบายที่เจ้าของจัดเตรียม |
| หลังบ้าน | Dashboard เนื้อหา ไฟล์ หมวด คำถาม สมาชิก โฆษณา รายงาน และตั้งค่า |
| ตั้งค่า/ยืนยัน 2FA และกู้คืนบัญชีทีมงาน | ลงทะเบียน TOTP ยืนยันรหัส เก็บรหัสกู้คืน และขั้นตอนฉุกเฉินตาม NFR-01 |
| หน้าสถานะ 404 / 403 / 500 / 503 | ไม่พบหน้า สิทธิ์ไม่พอ ระบบขัดข้อง และปิดปรับปรุงชั่วคราว |

## 6. สถาปัตยกรรมและเครื่องมือที่เสนอ

แนวทางพัฒนารุ่นแรกใช้เว็บแยกส่วนหน้าบ้านและ API หลังบ้าน โดย Next.js แสดงหน้าเว็บที่เผยแพร่ให้ crawler อ่านได้และเรียก Go API เพื่ออ่าน/เขียนข้อมูล ส่วน Go API เป็นผู้ตรวจสอบตัวตน สิทธิ์บทบาท และสิทธิ์ Member/VIP ที่ฝั่งเซิร์ฟเวอร์ก่อนส่งข้อมูลหรืออนุญาตการกระทำทุกครั้ง

| ส่วนงาน | เครื่องมือหลักที่เสนอ | แนวทางใช้งาน |
|---|---|---|
| Frontend และ SSR/SSG | Next.js (React) | เรนเดอร์หน้าเนื้อหาสาธารณะฝั่งเซิร์ฟเวอร์เพื่อ SEO และรองรับการเปลี่ยนหน้าอย่างราบรื่น |
| UI และ CSS | shadcn/ui + Tailwind CSS | ใช้เป็นชุดส่วนประกอบและระบบจัดรูปแบบที่ปรับเข้ากับแบรนด์ BAN BUNSI ได้ |
| ไอคอน | Lucide React | ใช้ไอคอนสไตล์เดียวกัน และมีข้อความกำกับการทำงานที่สำคัญ |
| กราฟหลังบ้าน | Recharts | แสดงสถิติและรายงานใน Dashboard |
| Backend API | Go + Fiber | ให้บริการ REST API; Gin เป็นทางเลือกได้หากทีมพัฒนาหรือการประเมินทางเทคนิคเห็นว่าเหมาะกว่า |
| API contract | REST + OpenAPI | จัดทำสัญญา API และเอกสารสำหรับทีม Frontend/Backend ให้สอดคล้องกัน; พิจารณา gRPC เฉพาะเมื่อมีข้อกำหนดการสื่อสารระหว่างบริการที่ชัดเจน |
| ฐานข้อมูลและ toolkit | PostgreSQL + GORM หรือ Ent | เก็บข้อมูล CMS บัญชี สมาชิก สิทธิ์ และประวัติ โดยเลือก ORM ให้ตรงกับความถนัดและรูปแบบข้อมูลของทีม |
| ไฟล์และสื่อ | AWS S3 หรือ Cloudflare R2 | เก็บไฟล์ private และไฟล์ public แยกตามการใช้งานและสิทธิ์ใน FR-02/FR-03; การเข้าถึงไฟล์ private ต้องผ่านการตรวจสิทธิ์ของ API ทุกครั้ง |
| Rich Text Editor | Tiptap หรือ BlockNote | เขียนและแก้ไขเนื้อหา Rich Text ตามความสามารถใน FR-01 |
| ฟอร์มและ validation | React Hook Form + Zod | ตรวจข้อมูลฟอร์มฝั่งหน้าเว็บ และตรวจซ้ำ/บังคับกฎด้านความปลอดภัยที่ API |

การเลือกตัวเลือกสุดท้ายระหว่าง Fiber/Gin, GORM/Ent, S3/R2 และ Tiptap/BlockNote ให้ยืนยันก่อนเริ่มพัฒนา โดยยึดความสามารถในการดูแลระบบ ต้นทุน และประสบการณ์ของทีมเป็นเกณฑ์ การตรวจสิทธิ์ การเผยแพร่ การจัดเก็บความลับ และการบังคับ validation ที่มีผลต่อความปลอดภัยต้องทำที่ Backend เสมอ ไม่ถือว่าการตรวจบน Frontend ทดแทนได้
